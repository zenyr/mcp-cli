# Bun·txiki.js 공통 실행 검증

MCP 호출 로직을 공유하면서 런타임 구현만 교체할 수 있는지 확인하는 실험입니다.
실제 CLI의 기본 런타임이나 배포 방식은 변경하지 않습니다.

## 구성

- `runtime.ts`: 프로세스의 입출력 스트림, 로컬 HTTP 서버, 파일 저장의 공통 계약
- `bun-runtime.ts`, `txiki-runtime.ts`: 두 런타임의 구현
- `probe.ts`: 공통 실행 진입점과 런타임 선택
- `oauth.ts`: 공식 MCP SDK로 메타데이터 조회, 동적 클라이언트 등록, PKCE 로그인과 토큰 갱신
- `stdio.ts`: 런타임의 프로세스 스트림을 공식 SDK의 연결 계약에 연결하는 구현과 로컬 검증 서버
- `verify.ts`: 두 실행 파일의 빌드, 로컬 서버 실행과 결과 비교

MCP·OAuth 처리는 공통 코드에 두고 런타임별 차이는 두 구현 파일에 둡니다.
Node나 Bun 전체를 흉내 내는 호환 계층은 만들지 않습니다.
공통 코드에는 `node:*`, `bun:*`, `tjs:*` import가 없습니다.

## 감지와 빌드 시 선택

`BUILD_RUNTIME`이 `auto`이면 `typeof Bun`으로 구현을 선택합니다.
검증기는 이 경로도 Bun 실행 파일로 빌드해서 시험합니다.
Bun용 결과물에는 런타임이 내장되어 있으므로 PATH에 Bun이 없어도 자동 감지는 Bun을 선택합니다.

배포용 결과물은 `BUILD_RUNTIME`을 `bun`이나 `txiki`로 고정합니다.
동적 import 분기에 빌드 상수를 직접 사용하면 번들러가 선택하지 않은 분기를 제거합니다.
이 실험에서는 Bun 번들러를 사용하며 txiki.js용 자바스크립트에 Bun의 프로세스 구현과 Node import가 남지 않는지 검사합니다.
런타임에서 감지하는 분기는 빌드 상수만으로 정해지는 분기와 다릅니다.
자동 감지만으로 두 구현의 의존성이 번들에서 제거된다고 보장할 수는 없습니다.

현재 txiki.js의 `fetch`는 SDK가 넘기는 URL 객체 대신 문자열을 받도록 구현 안에서 변환해야 합니다.
SDK의 Node 전용 `StdioClientTransport`는 재사용하지 않습니다.
공식 SDK의 프로토콜 처리는 유지하고 프로세스 스트림 연결만 공통 구현으로 대체합니다.

## 실행

저장소 루트에서 실행합니다.

```sh
bun install --frozen-lockfile
TJS_BIN=/absolute/path/to/tjs bun run --cwd packages/mcp probe:txiki
```

`TJS_BIN`을 생략하면 PATH의 `tjs`, 다음으로 `~/.tinyjs/bin/tjs`를 찾습니다.
stdio만 검증하려면 다음 명령을 사용합니다.

```sh
TJS_BIN=/absolute/path/to/tjs bun run --cwd packages/mcp probe:txiki --stdio-only
```

빌드와 로컬 서버를 실행하는 검증기에는 Bun이 필요합니다.
검증 대상 클라이언트와 stdio 서버는 각각 컴파일한 실행 파일입니다.
실행 단계에서는 PATH를 비어 있는 임시 폴더로 바꿉니다. 외부 Bun이나 tjs 명령을 찾을 수 없는 상태에서 실행합니다.
컴파일과 실행에 쓴 임시 파일은 끝날 때 삭제합니다. 실제 계정과 사용자 자격 증명은 사용하지 않습니다.

결과는 표준 출력에 JSON으로 반환합니다. 실패한 항목이 있으면 종료 코드 1입니다.
런타임 하나의 검증이 실패해도 나머지 항목은 계속 검사합니다.
일반 `bun run check`에는 타입 검사만 포함합니다. 네이티브 런타임 검증은 위 명령으로 별도 실행합니다.

## 검사 범위

- JSON 응답 방식의 Streamable HTTP: 연결, 도구 목록과 도구 호출
- stdio: 여러 요청·응답, 7바이트씩 나눠 전송한 한글·이모지와 정상 종료
- OAuth: 메타데이터 조회, 동적 클라이언트 등록, S256 PKCE와 실제 로컬 콜백 서버
- 토큰 파일 저장·재조회·갱신과 갱신한 토큰을 사용한 MCP 호출
- POSIX 토큰 파일의 `0600` 권한과 표준 출력의 토큰 노출 여부
- 잘못된 `state`와 `access_denied` 거부, 거부한 인증의 파일 미생성
- 런타임 고정 빌드와 Bun 자동 감지 빌드의 결과 비교

검증용 OAuth 서버는 받은 요청의 `Host`가 아니라 자신의 주소를 기준으로 메타데이터를 만듭니다.
설치된 txiki.js에서 요청의 `Host`에 포트가 빠지는 현상을 관측했으므로 실제 서버의 호스트 기반 라우팅도 후속 검증이 필요합니다.

## 관측 결과

2026-10-20, macOS arm64에서 검증했습니다.

설치된 tinyjs v0.42.0의 txiki.js v26.6.0에서는 HTTP와 OAuth 항목이 통과했습니다.
stdio는 첫 쓰기를 전달한 뒤 완료 대기가 풀리지 않아 실패했습니다.
이는 [upstream 수정 c1f48603](https://github.com/saghul/txiki.js/commit/c1f48603f1b22755fc79ab473bbc67d1926793f5)의 설명과 일치합니다.

upstream `8a9b604` 소스를 별도 빌드한 실행 파일에서는 같은 stdio 검증이 통과했습니다.
이 빌드에서는 HTTP 호출 중 종료 코드 139를 관측했습니다. 원인은 확정하지 않았습니다.
두 빌드 모두 버전 문자열은 v26.6.0이므로 소스 리비전도 함께 기록해야 합니다.
로컬에 설치된 tinyjs 실행 파일은 교체하지 않았습니다.

Bun에서는 런타임 고정 경로와 자동 감지 경로가 모두 전체 항목을 통과했습니다.
이번 빌드의 실행 파일은 Bun 63,069,042바이트, 설치된 txiki.js 6,356,819바이트, upstream 소스 빌드 6,789,528바이트였습니다.
이는 실험 프로그램의 크기이며 전체 CLI 배포물의 크기가 아닙니다.

현재 증거는 공통 계약과 런타임 교체 방식의 실행 가능성을 보여줍니다.
검증한 txiki.js 빌드 하나로 모든 항목이 통과한 상태는 아닙니다.
기본 배포를 바꾸기 전에 사용할 리비전을 고정하고 전체 검증을 다시 통과해야 합니다.

## 실제 CLI에 적용하기 전

플러그인 탐색과 정적 생성 파일 로딩, 프로세스 간 인증 잠금, 대몬 IPC, Fish Audio의 ffmpeg 실행은 아직 옮기지 않았습니다.
`mem`의 SQLite도 이 검증 범위에 포함하지 않습니다.
SSE 응답, 인증 만료 시각에 따른 자동 갱신, 동시 갱신 잠금, 외부 브라우저와 실제 서비스 로그인은 별도 검증이 필요합니다.
현재 토큰 저장 구현은 실험용이며 운영용 자격 증명 저장소를 대체하지 않습니다.
